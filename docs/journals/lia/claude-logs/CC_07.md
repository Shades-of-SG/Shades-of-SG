useEffect(() => {

Database changes (apply manually in Supabase)
Only one schema change is needed across both features — everything else uses existing columns.

Migration: make moderation_actions.actor_id and folders.created_by nullable, so that when a user is hard-deleted, the audit/history rows that reference them (as the person who took an action) can be kept with that reference set to null instead of being blocked or deleted outright. Today both columns are NOT NULL with a RESTRICT-style FK, which would otherwise make it impossible to delete a user who has ever issued a moderation action or created a folder (this includes creators, not just admins — creators write ModerationAction rows via reflection moderation and Folder.createdBy via folder creation).

Run this in Supabase's SQL editor (matches backend/migrations/026_account_hard_delete.sql, which is created alongside this change for the repo's migration history):

begin;

alter table moderation_actions alter column actor_id drop not null;
alter table moderation_actions drop constraint if exists moderation_actions_actor_id_fkey;
alter table moderation_actions add constraint moderation_actions_actor_id_fkey
    foreign key (actor_id) references users(id) on delete set null;

alter table folders alter column created_by drop not null;
alter table folders drop constraint if exists folders_created_by_fkey;
alter table folders add constraint folders_created_by_fkey
    foreign key (created_by) references users(id) on delete set null;

commit;
No other tables need schema changes:

All other tables that reference users(id) already have a workable ON DELETE CASCADE/SET NULL/nullable-column shape for what this plan needs, or the hard-delete service deletes those rows explicitly in code before removing the user (so it doesn't rely on the DB constraint at all for those).
songs.creator_id stays NOT NULL/RESTRICT intentionally — deleting a creator deletes their songs (with a published-content guard/confirmation), rather than orphaning them; no migration needed for that.
No new tables are introduced by either feature.
If you'd rather not run this migration, the fallback is: the hard-delete service must delete (not null-out) any ModerationAction/Folder rows that reference the user being deleted whenever it hits this constraint, which loses those specific audit/history entries entirely instead of preserving them anonymized. I recommend running the migration so audit history is preserved — flag if you'd prefer the fallback instead.
