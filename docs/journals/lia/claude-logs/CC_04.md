# Claude Plan:
Auth flow fixes: password validation, show/hide, OTP resend cooldown
Context
The Login, Register, Forgot Password, and Reset Password flows have several inconsistencies and one real bug:

Password complexity isn't enforced anywhere (only length 8-128), so weak passwords are accepted on registration and password reset.
ResetPassword.jsx's two password fields have no show/hide toggle, unlike Login/Register.
ResetPassword.jsx's "Request another code" button has no client-side cooldown, so clicking it repeatedly hits the backend's 60s OTP cooldown — but POST /password-reset/request always swallows errors and returns a generic 202 "code will be sent" message (this is intentional for privacy: it stops attackers from telling which emails are registered). The user sees a false "sent" message while the old code silently remains the only valid one.
Email format validation is inconsistent (Login/Register have a regex; ForgotPassword/ResetPassword rely only on the native type="email" input).
Explicit descoping: I proposed adding a real-time "does this email exist in the DB" check for Login/Forgot Password/Register, matching the literal ask. The user declined this — it would add a new enumeration oracle (anyone could probe which emails are registered), which conflicts with the app's existing enumeration-safe design (see the comment at backend/routes/auth.js:225). No "email exists" check will be built. Only real-time format validation (regex, debounced) is in scope. There is also no separate authenticated "change password" feature in the app today — Settings just links to the Forgot Password flow — so "changing passwords" in the requirements maps to the Reset Password flow, not a new feature.

The OTP-resend cooldown fix is not an enumeration regression: the 60s cooldown only ever fires for an email that has already had a code issued in this browser flow (i.e., the requester already knows the account exists), so surfacing "please wait Ns" for that case leaks nothing new. All other password-reset/request errors keep being swallowed into the generic 202, preserving the existing privacy guarantee for unknown/ineligible emails.
